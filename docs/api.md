# 🔌 مرجع API (API Reference)

> **برای چه کسی؟** کسی که با سرور کار می‌کند (فرانت‌اند یا هر مصرف‌کننده‌ی دیگر).
> **وضعیت فعلی:** ⚪ **هنوز هیچ API‌ای وجود ندارد** — این واقعیت است، نه کم‌کاری.

## چرا این سند مهم است

طبق بازرسی مخزن (۲۰۲۶-۱۰-۰۴): پوشه‌ی `backend/` فقط `README.md` دارد؛
نه سروری هست، نه `package.json`، نه endpoint‌ای. بنابراین:

- **هیچ endpoint‌ای مستند نشده چون هیچ endpoint‌ای پیاده‌سازی نشده.**
- هر ادعایی درباره‌ی مسیر/پاسخ/کد خطا در این مرحله **اختراع** بود — پس نوشته نمی‌شود.

این فایل از همین‌حالا «قرارداد قالب» را نگه می‌دارد تا اولین endpoint واقعی، درست ثبت شود.

## قالب مستندسازی هر endpoint

برای **هر** مسیر این قالب را رعایت کن:

```md
### `METHOD /path` — عنوان فارسی

- **چه زمانی استفاده می‌شود:** ...
- **دسترسی:** عمومی / نیازمند توکن
- **ورودی (Body/Params):**
  | فیلد | نوع | ضروری | توضیح |
- **خروجی موفق:** نمونه JSON
- **خطاهای محتمل:** `400` / `401` / `404` / ...
```

## فهرست endpoint ها

| متد | مسیر | عنوان | وضعیت |
|---|---|---|---|
| — | — | **هیچ endpoint‌ای وجود ندارد** | ⚪ منتظر `/Build` |

## چه زمانی این صفحه پر می‌شود؟

```text
/PRD   → طراحی API (Method/Path/Auth/Input/Output/Errors)
/Build → پیاده‌سازی + تست واقعی
/Doc   → هم‌راستاسازی نهایی این صفحه با خروجی واقعی
```

## قواعد حین پیاده‌سازی (از `conventions.md` و `skills/build`)

- مسیرها فقط `route → service → db` را طی می‌کنند؛ منطق داخل route ممنوع.
- نمونه‌های JSON باید **از خروجی تست واقعی** باشند، نه ساختگی.
- هر endpoint جدید، **همان‌لحظه** به همین فایل اضافه شود.
- مستندسازی از جنس `Documented` ≠ `Verified` — ادعای verify‌نشده ممنوع.
