# `/check` — دروازه‌ی اعتبارسنجی VCNO (مرحله ۲)

> **مأموریت: «آیا آن‌قدر می‌فهمیم که بتوانیم یک PRD قابل‌اعتماد بسازیم؟»**
> `/check` بین `/init` و `/PRD` است: ایده، نیازمندی‌ها، محدودیت‌ها، فرض‌ها، امکان‌سنجی، ریسک‌ها و اطلاعات غایب را اعتبارسنجی می‌کند. نه مرحله‌ی برنامه‌ریزی است، نه مرحله‌ی کدنویسی.

| | |
|---|---|
| Command | `/check` |
| Stage | 2 — VCNO |
| Version | 1.0.0 — stable |
| Previous stage | `/init` |
| Next stage | `/PRD` |

## مرز مرحله (سخت‌گیرانه)

```text
/init  → Understand    (جمع‌آوری context)
/check → Validate      ← این اسکیل
/PRD   → Plan          (طراحی و تفصیل)
/Build → Implement
/Feedback → Improve
/Doc   → Finalize
```

- `/check` **ممکن است** تشخیص دهد که تصمیم معماری لازم است — اما **نباید** معماری کامل را تحویل دهد.
- `/check` **ممکن است** بگوید schema لازم است — اما **نباید** schema را طراحی کند.

## چه زمانی اجرا شود

- بعد از اتمام `/init` (یا ادامه‌ی آن اگر `NEEDS_INPUT` بود)
- قبل از هر اجرای `/PRD`
- هر وقت نیازمندی‌ها مبهم، متناقض یا بیش‌ازحد بزرگ به‌نظر می‌رسند

## پیش‌نیازها

- خروجی `/init`: `docs/project.md` و `docs/logs/init.md` (یا معادل)
- دسترسی خواندنی به مخزن و Git
- **هیچ نصب، پیاده‌سازی یا بازآرایی مجاز نیست**

## قرارداد رفتار

### MUST

- خروجی `/init` را مصرف کن (context ثبت‌شده را دوباره نپرس)
- ایده، نیازمندی‌ها، MVP، امکان‌سنجی و محدودیت‌ها را اعتبارسنجی کن
- نیت کاربر را با واقعیت مخزن مقایسه کن (reality check)
- تناقض، scope creep و فرض‌های پنهان را کشف کن
- واقعیت‌ها را جدا نگه دار: `Confirmed` / `Inferred` / `Unknown` / `Needs clarification`
- فقط سؤال‌های پرتأثیر بپرس؛ با جواب‌ها iterate کن
- با یک وضعیت آمادگی صریح تمام کن
- کار کاربر و secretها را حفظ کن

### MUST NOT

- پیاده‌سازی، refactor، بازآرایی یا deploy کن
- dependency پروژه را نصب کن
- معماری یا schema کامل را طراحی کن (کار `/PRD` است)
- سؤال‌هایی را که `/init` پاسخ داده دوباره بپرس
- ابهام مهم را بی‌سروصدا حل کن
- requirement یا تکنولوژی اختراع کن
- بدون احراز معیارها `READY FOR PRD` ادعا کن

## مراحل کار

1. **بارگذاری context `/init`** — `docs/project.md`، `docs/logs/init.md`، داکس/PRD/specهای موجود، stack و دارایی‌های تشخیص‌داده‌شده. قانون: واقعیت ثبت‌شده → استفاده کن، نپرس؛ unknown ثبت‌شده → تلاش برای رفعش؛ `NEEDS_INPUT` بود → اول ورودی غایب را حل کن.
2. **Reality check مقابل مخزن** — نیت اعلام‌شده را با کدِ قابل‌مشاهده مقایسه کن. «احراز هویت لازم داریم» درحالی‌که auth موجود است → به‌عنوان «موجود» علامت بزن، تکرار نساز؛ schema موجود → در اعتبارسنجی ارجاع بده؛ frontend موجود → شکاف‌ها را validate کن، نه بازسازی.
3. **اعتبارسنجی محصول/ایده** — چه چیزی، چرا، چه مشکلی، کاربر هدف، نتیجه‌ی موردنظر، حداقل نسخه‌ی مفید، out-of-scope صریح. جملات مبهم («مدرن بساز»، «مثل X»، «پلتفرم AI») را به الزام مشخص/قابل‌سنجش، یا سؤال متمرکز، یا `Needs clarification` تبدیل کن.
4. **اعتبارسنجی نیازمندی‌ها** — برای هر requirement: وضوح، سازگاری، قابل‌تست‌بودن، دست‌یافتنی‌بودن، کفایت جزئیات، اولویت. کشف کن: غایب، متناقض، غیرضروری، تکراری، فرض پنهان، scope creep، اصطلاحات نامشخص. ابهام مهم را حلِ خاموش نکن — ثبتش کن و در صورت اهمیت بپرس.
5. **اعتبارسنجی MVP** — هر requirement کاندید را دسته‌بندی کن: `Must Have` / `Should Have` / `Could Have` / `Out of Scope` / `Unknown`. هر اشاره‌ی کاربر را خودکار به V1 ارتقا نده؛ ایده‌ها را رد نکن — طبقه‌بندی کن؛ کوچک‌ترین نسخه‌ی معنادار را صریح نام‌گذاری کن.
6. **اعتبارسنجی فنی** — بدون پیاده‌سازی: زبان/فریم‌ورک/دیتابیس، API، auth، infra، deploy، سرویس‌های خارجی، performance و security، مقیاس‌پذیری. سؤال: «آیا این فنی آن‌قدر فهمیده شده که قابل‌برنامه‌ریزی باشد؟» — نه «بیا کد بزنیم». تعیین‌ناپذیر → `Unknown` / `Needs clarification`؛ اختراع ممنوع.
7. **بازبینی دارایی‌ها** — کد، schema/مایگریشن، کانفیگ، داکس، عکس/Figma/PDF، مستندات API، PRDهای قبلی، تست‌ها. دارایی‌های UI ورودی‌اند و به requirement تبدیل می‌شوند؛ phase جداگانه‌ی UI-design اجباری نساز؛ دارایی‌ها را تغییر نده.
8. **تحقیق هدفمند (فقط در صورت نیاز)** — تکنولوژی ناآشنا، محدودیت API/فریم‌ورک/طرف‌ثالث، محدودیت قانونی/پلتفرم، امکان‌پذیری فنی. یافته‌ها را ثبت کن: `Verified` / `Inferred` / `Unknown` / `Needs confirmation`. برای شباهت ظاهری تحقیق نکن.
9. **تشخیص تناقض** — مثال: «اپ آفلاین» + «وابسته به API ابری زنده»؛ «MVP حداقلی» + «۲۰ ماژول برای V1». پیدا → توضیح تضاد → سؤالِ clarification → **هرگز خاموش یک طرف را انتخاب نکن.**
10. **تشخیص ریسک** — فقط ریسک‌های خاصِ پروژه (دامنهی غیرواقعی، API دردسترس‌نبودن، مدل کسب‌وکار مبهم، امنیت/حریم خصوصی، bottleneck، vendor lock-in، infra غایب، مالکیت مبهم، الزام ناممکن، پیچیدگی بیش‌ازحد، محدودیت قانونی/پلتفرم). رتبه‌بندی: `Critical / High / Medium / Low`. لیست ریسک عمومی ممنوع.
11. **سؤال‌های متمرکز** — فقط وقتی جواب بر برنامه‌ی محصول/فنی اثر مادی بگذارد. قالب:

    ```markdown
    ## Questions
    ### 1. <Question>
    Current understanding: ...
    Why this matters: ...
    ```

    هر بار ده‌ها سؤال نپرس؛ چیزی را نپرس که مخزن یا `/init` جواب داده.
12. **حلقه‌ی تکرار اعتبارسنجی** — تحلیل → شکاف → سؤال → جواب کاربر → بازبینی → باقی‌مانده؟ بله → حلقه؛ خیر → approval. اولین گذشته را کافی فرض نکن؛ با جواب جدید context را به‌روز کن (از صفر شروع نکن)؛ آمادگی را بعد از هر تکرار دوباره حساب کن.
13. **انضباط واقعیت‌ها** — `## Confirmed` (مستقیم دیده/گفته‌شده) / `## Inferred` (قویاً پیشنهادشده) / `## Unknown` (تعیین‌ناپذیر) / `## Needs User Confirmation` (قبل از پیشروی امن باید جواب داده شود). فرض هرگز خاموش به requirement قطعی تبدیل نشود.
14. **حفاظت از دامنه** — اضافه‌ها: `V1 / Future / Optional / Out of Scope / Needs validation`. ایده‌ها را رد نکن؛ مانع شو که دلبخواهی به V1 اجباری تبدیل شود.
15. **مستندسازی** — فقط وقتی مفید و طبق قاعده‌ی موجود: `docs/logs/check.md` (یا `docs/check/…` اگر ساختار موجود پشتیبانی می‌کند). شامل: نیازمندی‌های اعتبارسنجی‌شده، تصمیم‌ها، سؤال‌های حل‌نشده، ریسک‌ها، مرز دامنه، یافته‌های فنی، وضعیت آمادگی. داکس زائد نساز؛ خروجی `/init` را تکرار نکن.
16. **ایمنی Git** — قبل از نوشتن، status را ببین؛ reset/clean/revert ممنوع؛ overwrite تغییر غیرمرتبط ممنوع؛ commit secret ممنوع؛ پیروی از قاعده‌ی commit پروژه؛ commit بی‌دلیل ممنوع.
17. **امنیت و حریم خصوصی** — API key، password، token، private key، session secret، credential دیتابیس هرگز در داکسِ اعتبارسنجی نرو. اگر credential دیدی، فقط وجودش را عمومی اشاره کن — نه مقدارش را.
18. **دروازه‌ی آمادگی** — هر اجرا دقیقاً با یکی از این‌ها تمام می‌شود:

    ```text
    NOT READY              ← requirement بحرانی حل‌نشده
    READY WITH WARNINGS    ← قابل‌پیشروی است؛ هر uncertainty غیرمسدودکننده فهرست شود
    READY FOR PRD          ← فقط با احراز معیارهای تکمیل
    ```

    معیار `READY FOR PRD` (هر کدام ناقص → ادعا نکن):

    ```text
    [ ] purpose پروژه مفهوم است     [ ] کاربران هدف مفهوم‌اند
    [ ] مشکل هسته‌ای مفهوم است      [ ] راه‌حل موردنظر مفهوم است
    [ ] دامنه‌ی MVP تعریف شده       [ ] requirementهای مهم شفاف‌اند
    [ ] تناقض‌های major حل شده      [ ] محدودیت‌های فنی مهم فهمیده شده
    [ ] پیاده‌سازی موجود لحاظ شده   [ ] دارایی‌های مرتبط لحاظ شده
    [ ] ریسک‌های مهم شناسایی شده    [ ] unknownهای بحرانی حل شده
    [ ] کاربر فرصت تأیید جهت را داشته
    ```

    طولانی‌بودن تحلیل دلیل آمادگی نیست؛ خوش‌بینی برای راضی‌کردن کاربر دلیل آمادگی نیست.

## خروجی مورد انتظار

گزارش کوتاه و اسکن‌پذیر (اگر مخزن قالب خاص دارد، همان):

```markdown
# VCNO Check
## Project
## Understanding
## Validated Requirements
## MVP Scope
## Technical Reality
## Existing Assets
## Risks
## Contradictions
## Unknowns
## Questions
## Decisions
## Readiness
NOT READY | READY WITH WARNINGS | READY FOR PRD
## Next Step
```

پاسخ نهایی باید صریح بگوید: چه چک شد، چه تأیید شد، چه فهمی عوض شد، چه چیزی ناشناخته ماند، چه سؤال‌هایی مانده، آیا آماده‌ی `/PRD` است و کاربر بعد چه کند:

```text
Status: READY WITH WARNINGS
Next step: سؤال‌های بالا را جواب بده و /check را دوباره اجرا کن.
یا (حل‌شده): Next step: Run /PRD.
```

## نکات و خطاهای رایج

- **خطای ممنوع:** `/check → ساخت فیچر / نوشتن کد production / طراحی مجدد / refactor / مهاجرت دیتابیس / نصب dependency / دست‌زدن به source غیرمرتبط / deploy / ادعا موفقیت پیاده‌سازی`.
- سؤال‌های تکراری از `/init` — اول context را بخوان.
- حلِ خاموشِ ابهام مهم — ثبتش کن و بپرس.
- ادعای `READY FOR PRD` بدون احراز چک‌لیست.
- ریسک‌های کلیشه‌ای بدون ارتباط با پروژه.

## یکپارچگی با خط لوله‌ی VCNO

| مرحله | رابطه |
|---|---|
| `/init` | context می‌دهد؛ `/check` مصرف می‌کند |
| `/PRD` | خروجی `/check` را مصرف می‌کند؛ blueprint می‌سازد |
| `/Build` | منتظر نیازمندی‌های معتبر از `/check → /PRD` |
| `/Feedback` | تصمیم‌ها و سؤال‌های باز `/check` را anchor قرار می‌دهد |
| `/Doc` | رکورد نهایی اعتبارسنجی را جذب می‌کند |

`/check` آماده می‌کند؛ هرگز طرح نمی‌سازد.

## اصل راهنما

> نگذار ایجنت چیزی را که واقعاً نمی‌فهمد برنامه‌ریزی یا بسازد.

- `/init` → Understand
- `/check` → Validate
- `/PRD` → Plan
- `/Build` → Implement
- `/Feedback` → Improve
- `/Doc` → Finalize

`/check` **دروزه‌ی کیفیت بین فهم و برنامه‌ریزی** است — نه فاز کدنویسی دیگر.
