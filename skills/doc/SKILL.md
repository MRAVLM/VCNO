# `/Doc` — مرحله‌ی نهایی‌سازی VCNO (مرحله ۶)

> **مأموریت: «اگر امروز توسعه‌دهنده‌ی دیگری این مخزن را بگیرد، می‌فهمد چیست، چطور اجرا و نگهداری می‌کند و محدودیت‌های فعلی‌اش را می‌داند؟»**
> `/Doc` مستندات را با پیاده‌سازی واقعی هم‌راستا می‌کند. **واقعیت را مستند می‌کند، نه نیّت را.**

## مرز مرحله

```text
/init → /check → /PRD → /Build → /Feedback ↺ → /Doc
```

- **پیاده‌سازی نهایی منبع حقیقت است**
- `/Doc` مستند می‌کند؛ پیاده نمی‌کند، refactor نمی‌کند، رفع اشکال نمی‌کند
- فیچر غایب را پیدا کرد → **مستندش کن که غایب است، نسازش**
- اگر فیچر غایب release را مسدود کرد → `BLOCKED` و بازگشت به `/Build` یا `/Feedback`
- مستندات باید متناسب با پیچیدگی پروژه باشد

## چه زمانی اجرا شود

- بعد از `/Build` و `/Feedback` وقتی پروژه به وضعیت قابل‌تحویل/قابل‌انتشار نزدیک شد
- دوره‌ای برای هم‌راستاسازی کل داکس با واقعیت
- قبل از release یا تحویل به توسعه‌دهنده‌ی دیگر

## پیش‌نیازها

- خروجی همه‌ی مراحل: `/init`، `/check`، `/PRD`، گزارش `/Build`، تاریخچه `/Feedback`
- دسترسی به مخزن واقعی (کد، کانفیگ، Git)
- **صداقت درباره‌ی verification** — از PRD حکایت نکن؛ از پیاده‌سازی حکایت کن

## قرارداد رفتار

### MUST

- قبل از مستندسازی، پروژه را بازرسی کن
- داکس موجود را قبل از ساختِ جدید audit کن
- به‌جای ساخت duplicate، موجود را به‌روز کن
- وقتی README، PRD، کد و داکس تناقض دارند، آن‌ها را reconcile کن
- تمایز بده: `Documented` / `Verified` / `Not Verified` / `Unknown`
- secret را حفظ کن؛ credential هرگز در داکس کپی نشود
- محدودیت‌های شناخته‌شده را صادقانه مستند کن
- آمادگی تحویل/انتشار را بر اساس evidence ارزیابی کن
- کار کاربر و وضعیت Git را حفظ کن

### MUST NOT

- وعده‌ی PRD را به‌جای آنچه ساخته شد مستند کن
- دستور، نسخه، endpoint یا معماری اختراع کن
- هر سندِ ممکن را «برای هر صورت» بساز
- secret/token/credential را افشا کن
- فیچر طراحی‌شده را پیاده‌شده علامت بزن
- بدون مدرک `READY FOR RELEASE` ادعا کن
- فیچر غایب را پیاده کن؛ باگ را خاموش رفع کن؛ معماری را طراحی مجدد کن
- PRD را برای پنهان‌کردن شکاف بازنویسی کن
- README غول‌پیکر، API reference تکراری یا داکسِ کدِ بدیهی تولید کن

## مراحل کار

1. **بارگذاری context** — خروجی `/init` (`docs/project.md`، init log)، رکورد `/check`، blueprint `/PRD`، گزارش و پیشرفت `/Build`، تاریخچه و وضعیت `/Feedback`، داکس موجود، Git status/commitهای اخیر، اطلاعات release/نسخه. **فقط از PRD مستند نکن.**
2. **بازرسی کامل پروژه** — کد، ساختار، README، کانفیگ، dependency، دیتابیس، API/auth، frontend/backend، تست‌ها، Docker/CI/CD، env، داکس، تاریخچه‌ی بازخورد، Git. **از نیّت مستند نکن.**
3. **Audit داکس موجود** — `README`، `CONTRIBUTING`، `CHANGELOG`، `docs/`، API/architecture/deployment، `.env.example`، داکس دیتابیس، developer/user guide. duplicate نساز؛ موجود را به‌روزرسانی درجا؛ اطلاعات مفید را حفظ؛ تناقض را رفع کن.
4. **انتخاب نوع داکس** — فقط آنچه پروژه واقعاً لازم دارد: README، نصب، کانفیگ، توسعه، معماری، API، دیتابیس، deploy، تست، troubleshooting، contributing، changelog، security، user guide. تولید همه برای هر پروژه ممنوع — **متناسب**.
5. **README** — در صورت لزوم توضیح بده: نام، چه می‌کند، چرا وجود دارد، فیچرهای اصلی، stack، پیش‌نیازها، نصب، کانفیگ، اجرا، تست، استفاده، ساختار، deploy، محدودیت‌ها، مشارکت، لایسنت. فقط بخش‌های مرتبط؛ یک توسعه‌دهنده‌ی جدید باید سریع بفهمد.
6. **مستندسازی نصب** — فرایندِ **واقعی**: پیش‌نیازها، نسخه‌ی runtime، نصب package، env، دیتابیس، migration، seed، build، startup. دستور باید با مخزن واقعی منطبق باشد؛ **دستور اختراع نکن؛ اگر verify نشده، بگو verify نشده.**
7. **متغیرهای محیطی** — فقط **نام و هدف**، هرگز مقدار: `DATABASE_URL`، `API_KEY`، `SECRET_KEY`. اگر مناسب بود `.env.example` با placeholder امن:

    ```env
    DATABASE_URL=
    SECRET_KEY=
    API_KEY=
    ```

8. **secretها و داده‌ی حساس** — قبل از نهایی‌سازی scan کن: API key، پسورد، token، private key، session secret، credential production، اطلاعات شخصی حساس. اگر در فایل tracked پیدا شد → **صریح flag کن، خود secret را در گزارش کپی نکن.**
9. **مستندسازی معماری** — برای پیچیدگی معنادار، معماری **واقعی**: مؤلفه‌های اصلی → مسئولیت‌ها → ارتباط → جریان داده → سرویس‌های خارجی. معماری‌ای که مؤلفه‌ی ناموجود را ادعا کند ممنوع.
10. **ساختار پروژه** — در صورت سودمندی و دقیق؛ dump درخت غول‌پیکر مگر اینکه واقعاً لازم باشد.
11. **مستندسازی API** — endpointهای مهم: `Method / Endpoint / Purpose / Auth / Input / Output / Errors`. اگر OpenAPI/Swagger موجود است → به‌روزرسانی همان، نه تکرار دستی.
12. **مستندسازی دیتابیس** — تکنولوژی، entityهای مهم، رابطه‌ها، فرایند migration، محدودیت‌ها، seed/setup. داده‌ی production حساس یا رکورد واقعی کاربر ممنوع.
13. **مستندسازی auth** — چگونه **واقعاً** کار می‌کند: جریان login، سازوکار session/token، نقش‌ها، مجوزها، منابع محافظت‌شده، کانفیگ، logout، بازیابی پسورد. credential مستند نشود.
14. **مستندسازی deploy** — فقط آنچه **واقعاً** پشتیبانی می‌شود: Dockerfile/compose، scriptها، CI/CD، hosting/proxy، env، process manager، migration. تمایز صریح `Documented configuration` vs `Verified deployment`; «موفقیت deploy در production» بدون verify ممنوع.
15. **مستندسازی تست** — فریم‌ورک، نحوه‌ی اجرا، ساختار، دسته‌های مهم، env لازم، محدودیت‌ها — فقط دستورهای منطبق با پروژه (اینجا: `npm run typecheck` و `npm run test` طبق `docs/conventions.md`).
16. **Troubleshooting** — فقط در صورت سودمندی و برای مشکلات تکرارپذیر/مهم پروژه: `Problem → Cause → Solution`. generic و بی‌ربط ممنوع.
17. **محدودیت‌های شناخته‌شده** — صادقانه: «API خارجی credential لازم دارد» / «deploy production verify نشده» / «فیچر X غیرفعال است» / «رفتار موبایل کامل تست نشده» / «خروجی AI ممکن است human verification بخواهد». داکس باید عدم قطعیت را بگوید، نه پنهان کند.
18. **وضعیت فیچر** — در صورت سودمندی: `Implemented / Partially Implemented / Experimental / Disabled / Planned / Known Issue`. طرح‌شده = پیاده‌شده **نشود**؛ «وجود فایل/tابع» دلیل تکمیل نیست.
19. **Changelog** — اگر موجود طبق قاعده‌ی خودش؛ اگر غایب و پروژه سود می‌برد → سبک بساز: `Added / Changed / Fixed / Security / Deprecated / Removed`. ویرایش ریز هر فایل ممنوع.
20. **نسخه و وضعیت release** — از منبع واقعی بازرسی کن: `package.json`، `pyproject.toml`، `__version__`، tagها. **نسخه اختراع نکن**؛ اگر استراتژی versioning وجود ندارد تحمیلش نکن مگر پروژه لازم داشته باشد.
21. **Git و آمادگی release** — branch، working tree، commitهای اخیر، untracked/ignored، tagها. قبل از نهایی: overwrite ممنوع، reset ممنوع، clean ممنوع، commit secret ممنوع. اگر پروژه برای release است، Git state را به‌اندازه‌ی کافی تمیز بسنج.
22. **Documented vs Verified** — همیشه تمایز بده: «کانفیگ deploy وجود دارد.» ≠ «deploy با موفقیت در production تست شده.» هرگز این دو را قاطی نکن.
23. **چک‌کیفیت داکس** — قبل از تکمیل: **Accuracy** (منطبق با پیاده‌سازی)، **Completeness** (توسعه‌دهنده‌ی جدید می‌فهمد و راه می‌اندازد)، **Consistency** (README/PRD/کد/داکس متناقض نیستند)، **Reproducibility** (نصب قابل‌تکرار)، **Security** (بدون secret)، **Maintainability** (قابل‌فهم می‌ماند).
24. **رفع/حذف داکس کهنه** — اگر اطلاعات واضحًا قدیمی است: به‌روزرسانی، حذف، یا علامت‌گذاری deprecated. حفظ اطلاعاتِ غلط فقط چون هست ممنوع.
25. **پرهیز از over-document** — README غول‌پیکر، API reference تکراری، essay معماریِ عظیم، داکسِ کدِ بدیهی، ورودیِ بی‌معنی changelog، راهنمای تکراری ممنوع. **کوچک، دقیق، مفید.**
26. **ساختار داکس** — طبق قاعده‌ی موجود (این پروژه: `docs/README.md` + فهرست). اگر هیچ قاعده نبود، پیش‌فرض معقول: `README.md` + `docs/{architecture,development,deployment,api,database,troubleshooting,changelog}.md`. **هر فایل را خودکار نساز** — فقط آنچه پروژه واقعاً سود می‌برد.
27. **وضعیت نهایی پروژه** — دقیقاً یکی:

    ```text
    DOCUMENTED             ← داکس با واقعیت هم‌راستاست
    READY FOR HANDOFF      ← تحویل به توسعه‌دهنده‌ی دیگر ممکن است
    READY FOR RELEASE      ← release آماده است
    PARTIALLY DOCUMENTED   ← بخشی ناقص است
    BLOCKED                ← شکاف release-سدکننده وجود دارد
    ```

    `READY FOR RELEASE` فقط چون داکس هست ادعا **نشود** — ممکن است به تست، deploy، امنیت، Git، کانفیگ، issueهای باز وابسته باشد.
28. **چک‌لیست release** (فقط اگر relevant؛ هر مورد فقط با verify واقعی تیک بخورد):

    ```text
    [ ] requirementها پیاده شد      [ ] تست‌ها پاس شدند
    [ ] باگهای بحرانی حل شد        [ ] مسائل امنیتی رسیدگی شد
    [ ] کانفیگ مستند شد            [ ] secretها محافظت شد
    [ ] README به‌روز شد            [ ] deploy مستند شد
    [ ] محدودیت‌ها مستند شد         [ ] نسخه verify شد
    [ ] وضعیت Git بازبینی شد       [ ] وضعیت release معلوم است
    ```

29. **آمادگی تحویل (Handoff)** — توسعه‌دهنده‌ی دیگر باید بتواند جواب دهد: این پروژه چیست؟ نصب؟ کانفیگ؟ اجرا؟ تست؟ چطور کار می‌کند؟ کد کجاست؟ API؟ دیتابیس؟ محدودیت‌ها؟ deploy؟ چه چیزی مانده؟ اگر از مخزن جواب‌پذیر نیست → داکسِ غایب را شناسایی کن.
30. **داکس در iterationهای آینده** — قاعده: `تغییر /Build یا /Feedback → به‌روزرسانی داکسِ متأثر در صورت نیاز → /Doc دوره‌ای همه‌چیز را reconcile می‌کند`. مستندسازی کار یک‌باره نیست.
31. **رابطه با مهارت‌های VCNO** — `/Doc` **نباید**: فیچر غایب را پیاده کند، باگ خاموش رفع کند، معماری طراحی مجدد کند، جای `/Build` یا `/Feedback` را بگیرد، PRD را برای پنهان‌کردن شکاف بازنویسی کند. فیچر غایب: `مستندش کن که غایب است → خودکار نساز`؛ اگر release را مسدود کرد: `BLOCKED → بازگشت به /Build یا /Feedback`.
32. **گزارش نهایی داکس** — هر اجرا با این تمام می‌شود:

    ```markdown
    # VCNO Documentation Report
    ## Status
    DOCUMENTED / READY FOR HANDOFF / READY FOR RELEASE
    / PARTIALLY DOCUMENTED / BLOCKED
    ## Documentation Updated / Created / Removed/Deprecated
    ## Project State
    ## Verified / ## Not Verified
    ## Known Limitations
    ## Release Readiness / ## Git
    ## Remaining Work
    ## Next Step
    ```

    فقط حقایقی با پشتوانه‌ی بازرسی یا verification واقعی.

## نکات و خطاهای رایج

- **خطای ممنوع:** `/Doc → مستندکردن وعده‌ی PRD به‌جای پیاده‌سازی / اختراع دستور، نسخه، endpoint، معماری / ساخت هر سندی برای هر صورت / افشای secret / علامت‌زدن فیچر طراحی‌شده به‌عنوان پیاده‌شده / ادعای READY FOR RELEASE بدون مدرک / پیاده‌سازی فیچر غایب / رفع خاموش باگ / طراحی مجدد معماری / بازنویسی PRD برای پنهان‌کردن شکاف / تولید داکسِ کم‌ارزشِ عظیم / قاطی‌کردن Documented و Verified**.
- فراموش‌کردن تمایز `Documented` vs `Verified`.

## یکپارچگی با خط لوله‌ی VCNO

| مرحله | رابطه |
|---|---|
| `/init` | context پروژه را می‌دهد |
| `/check` | نیازمندی‌های معتبر را می‌دهد |
| `/PRD` | طرح را می‌دهد (داکس باید بازسازیِ واقعی را بازتاب دهد، نه فقط طرح را) |
| `/Build` | واقعیتِ پیاده‌شده را می‌دهد |
| `/Feedback` | تاریخچه‌ی تکرار را می‌دهد |
| `/Doc` | هم‌راستا، مستند، نهایی می‌کند |

`/Doc` واقعیت را مستند می‌کند؛ آن را تغییر نمی‌دهد.

## اصل راهنما

> واقعیت را مستند کن، نه نیّت را.

- `/init` → Understand
- `/check` → Validate
- `/PRD` → Plan
- `/Build` → Implement + Verify
- `/Feedback` → Improve + Verify
- `/Doc` → Document + Reconcile + Finalize

مستندات نهایی باید وضعیت واقعی پروژه را روشن کند:

```text
چه چیزی وجود دارد / چه چیزی کار می‌کند / چه چیزی verify شد
چه چیزی verify نشد / چه چیزی غایب است / چه چیزی معلوم است
چه چیزی نامشخص است / چه چیزی باقی مانده
```

هرگز از داکس برای تمام‌نشده‌نشان‌دادنِ تمام‌نشده استفاده نکن. هدف `/Doc` این نیست که مخزن **کامل به‌نظر برسد**؛ این است که مخزن **کاملِ قابل‌فهم — یا صادقانه ناقص** باشد.
